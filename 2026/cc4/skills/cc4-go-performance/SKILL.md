# cc4 Go性能調査

## 前提と境界

- 当日マニュアル・アナウンス、現在の実装と計測を優先する。過去問の構成・点数・設定値を今年の仕様としない。
- cc4の第一候補はGo。言語変更は、制約の根拠・期待効果・移植範囲・検証時間・復元方法が揃う場合に検討する。
- 本戦情報は自チーム限定の非公開領域へ保存する。公開Gitへのpush、PR、コメント、ログ転送等を行わない。事前の公開TIPS更新許可を本戦の公開許可に引き継がない。
- このスキルは作業許可を拡張しない。ユーザーが依頼した調査・改善の範囲で進め、接続先と記録先を確認する。権限や期限の不足で進められない部分を報告する。

## 調査から変更を選ぶ

1. 加点するユーザー行動と前提API、FAIL条件、初期化・永続性を確認する。未確認項目は明示する。ベンチが未提供なら推測の採点モデルを作らない。
2. ソースと設定の所在・配備版を確認する。EC2から取得する場合は既存cloneと分離し、依存物・バイナリ・DBダンプ・大量ログ・秘密情報を選別する。SSH共通設定の所有者エラーにはユーザー設定の`-F`明示を検討し、ホスト鍵検証を維持する。
3. 現在の基準ベンチと負荷中の資源を確認する。配備・初期化・公式ベンチは直列に行う。DBや外部待ちが支配的なら、GoのCPU微調整を先にしない。
4. 回数と総時間からHTTP・SQLの支配的経路を特定する。CPU・メモリ・接続・ロック・I/O・通知/業務待ちを区別する。Go内の制約を調べる必要がある時だけ [Go計測](references/go-measurement.md) を読む。
5. 一つの仮説に必要な変更を選ぶ。結果の順序・認可・NULL・状態遷移・反映期限・二重処理・永続性を維持する条件を記録する。接続数・GC・バッファは測定した資源から決め、固定比率を適用しない。
6. 許可済みの改善作業なら実装・必要な検証・配備・公式ベンチまで進める。調査だけの依頼なら、根拠と候補を報告して範囲を広げない。初期化後にも変更が適用されること、実際に起動した版を確認する。
7. PASS、スコア、エラー、資源を比較して採用・復元を判断する。差が小さい場合や条件が変わった場合に再計測する。局所ベンチの改善を公式得点の改善と混同しない。

## 引き継ぐ出力

非公開の記録に「観測と根拠 → 仮説と得点への関係 → 変更/配備版 → 検証条件・結果 → 採否/復元 → 次の制約・未確認」を残す。ユーザー指定の目標・停止条件に達したら追加改善を止める。関係ないコード整理、全言語比較、外部ツールの一括導入、サブエージェント起動をこのスキルだけで追加しない。
