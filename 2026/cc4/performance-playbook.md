# 改善の手引き: 症状から仮説を選ぶ

作成日: 2026-10-07 JST。これはcc4向けの判断手順の提案で、2026の仕様や必勝手順ではない。背景と出典は [過去問調査](./past-contest-research.md)、入口は [当日の手順](./contest-start.md)。設定値は固定せず、実際の資源・ランタイム・負荷を確認する。

## 観測を選ぶ

| 層 | 最初に見るもの | 分かること・限界 |
| --- | --- | --- |
| OS | CPU、RSS、利用可能メモリ、I/O、ディスク、OOM、サービス状態 | 消費・停止・詰まりの層。高CPUだけで原因APIは分からない |
| HTTP | パス別の回数・合計時間・遅い側の時間・エラー・通信量 | 多数の軽い処理と少数の重い処理を比較。ログ書き込み自体の負荷もある |
| DB | クエリ別の回数・合計時間、実行計画、取得行数、ロック、接続待ち | SQL、過剰取得、排他、プール待ちを区別。遅い単発だけを見ない |
| アプリ | CPU/メモリのプロファイル、ハンドラ内の処理区間、待機 | 計算・割当・外部待ちの候補。計測方法によって見える対象が違う |
| シナリオ | 加点行動の完了数、各状態の滞留、ベンチエラー | サービスの改善と得点の関係。単純なHTTPスループットとは区別 |

導入済みツールとマニュアルから計測方法を選ぶ。例はOSのtop/free/vmstat、アクセスログ集計、DBのスロークエリ・統計、Goのpprof等。ツールの具体的操作・プロファイルの種類・設定は使うバージョンの公式資料で確認する。ベンチ外のアイドル観測だけで本番負荷を判断しない。

## 症状別の候補

### DB検索の総時間が大きい

確認: 高頻度クエリ、WHERE/JOIN/ORDER BY、既存インデックス、実行計画、読み取った行数、書き込み割合。

候補: 条件に合う複合インデックス、不要な列・行の取得削減、クエリの整理。インデックスの列順や範囲条件は実行計画で確認する。

検証: 結果集合・順序・ページ境界が同じか、書き込みや初期化が遅くならないか、次回初期化後にも変更が適用されるか。初手として必ず全テーブルにインデックスを追加する、という判断はしない。過去問例: 11予選・13・14。

### 一つの要求で同種の問い合わせを繰り返す

確認: ループ内SQL、共通関数の入れ子、要求あたりのクエリ数、件数増加との関係。

候補: 一括取得、JOIN、必要IDをまとめた取得、要求内での再利用。

検証: JOINによる重複、NULL、欠損、並び順、認可・テナント境界、メモリ増加。N+1をなくすために全データを無制限に読み込まない。過去問例: 13。

### 集計・ハッシュ・変換を何度も計算する

確認: 同じ入力の再計算、更新頻度、CPUプロファイル、集計クエリの総時間。

候補: 要求内の再利用、更新時の事前計算、集計値や結果のキャッシュ。

検証: キーの範囲、失効する更新、許容鮮度、初期化、再起動、複数プロセスでの一致。値が変わる場合の反映期限を当日仕様から確認する。過去問例: 13の画像ハッシュ。

### 待ち・ロック・接続が増える

確認: トランザクションの範囲、外部通信中のロック、DB接続数・待ち時間、アイドル接続、タイムアウト、排他の理由。

候補: 正しさを保てる範囲でのトランザクション短縮、接続再利用と上限調整、不要な直列処理の削減。

検証: 二重実行、競合、デッドロック、外部決済との整合性。プールを小さくし過ぎた待ちや、トランザクション内で別接続を必要とする処理にも注意。制限を外して並列数を増やすだけでは解決しない。過去問例: 12予選の排他。

### 書き込み増加に追いつかない

確認: 更新・INSERT・fsync・ロック・インデックス更新の時間、バッチの有無、要求の応答と確定の関係。

候補: 一括書き込み、更新処理の整理。キュー・遅延書き込みは仕様に適合する場合だけ検討する。

検証: 応答後の読取り、反映期限、順序、重複、再試行、キュー上限、終了時の未処理、再起動後の保持。メモリに置くだけで永続性を満たしたと考えない。過去問例: 11予選。

### 通知・状態遷移・割り当てが遅い

確認: 完了までの各状態の滞留、通知頻度、同時に処理できる数、距離・速度等の実際の制約、要求の依存。

候補: 複数件の処理、通知取得の効率化、割り当てアルゴリズムの改善。SQL時間が小さい場合も、業務処理の品質が負荷・得点へ影響し得る。

検証: 状態の順序、未通知の扱い、同一対象への重複割り当て、公平性、タイムアウト、計算時間。通知方式や反映猶予は年ごとの仕様に従う。過去問例: 14。

### CPU・メモリ・通信・ファイル処理が支配的

確認: プロファイル、RSS、利用可能メモリ、GC、ログ量、圧縮・ハッシュ、接続再作成、応答サイズ、DNSや外部サービス。

候補: 計算・割当・ログ量の削減、適切な接続再利用、仕様を保つ静的配信・条件付き応答、資源に合うメモリ上限。

検証: HTTPヘッダや条件付きリクエストの意味、内容の一致、ログ・計測の復元、OOM、ディスク不足。キャッシュやバッファの増大で別プロセスを圧迫しない。過去問例: 13のDNS・画像処理。設定変更前に実際のバージョンと有効値を確認する。

### 一台が飽和し、他の許可サーバーが空く

確認: データ所有、ローカルファイル、セッション、キャッシュ、DNS、通信・遅延、各ホストの負荷。

候補: アプリとDBの役割分離、アプリの複数台化、仕様に応じた分割。言語・DBの変更は別の候補として費用対効果を判断する。

検証: 初期化が全対象へ届くか、共有状態、更新反映、データ移行、ホスト障害・再起動、復元。ローカルの状態が別ホストにもあると仮定しない。過去問例: 12予選・12本選・13。

## FAILと障害を改善案から分ける

| 観測 | 次の確認 |
| --- | --- |
| 初期化で失敗 | スキーマ・データ・キャッシュ・外部接続のリセット、制限時間、SQLエラー |
| 整合性・通知・金額が不一致 | 最新差分、認可、順序、二重処理、失効、反映期限 |
| タイムアウト・502/504 | 上流サービス状態、OOM、接続・ロック待ち、要求の滞留 |
| PASSだが得点が変わらない | 加点経路、計測条件、次のボトルネック、ばらつき |
| 再起動後に壊れる | 起動設定、依存順序、揮発状態、永続データ、ファイル権限 |

FAILはスコア改善として採用しない。計測ログを残し、既知の正常版へ戻すか、原因を確認して修正する。ベンチ重複や配備途中の計測も有効な比較として扱わない。

## 仮説と実験の最小記録

```text
観測: 対象経路 / 時間・回数・資源 / ログやプロファイルへの参照
仮説: 何が何を待たせているか / 得点への関係
変更: 対象ファイル・SQL・設定 / 配備版
正しさ: 変えてはいけない結果・順序・認可・反映・永続性
検証: 必要なチェック / 公式ベンチ条件 / 計測による負荷
結果: PASS/FAIL / スコア / エラー / 資源 / 次の制約
判断: 採用・復元 / 理由 / 復元方法 / 未検証事項
```

初回の基準値と同条件で比較する。微差・ノイズ・負荷構成の変化が疑われる場合は反復して判断するが、失敗や新しい懸念がない検証を際限なく繰り返さない。限られた時間の中で、得点への寄与と安全に戻せる変更量から次の候補を選ぶ。
