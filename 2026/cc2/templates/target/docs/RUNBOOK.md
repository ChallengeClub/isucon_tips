# 対象別の操作手順

状態：チーム確認待ち。

この文書を非公開のtargetリポジトリにコピーし、実環境を読み取り確認して記入します。以下の例は架空の設定例であり、そのまま実行する指示ではありません。
ログインユーザーubuntu、アプリ実行ユーザーisucon、配置webappは例です。backend言語を含め実際の起動serviceで確認します。
このひな形に実行scriptは含みません。コマンド欄が未整備の操作は実行しません。

## 1. 準備

ローカルにBash・Python 3・SSHを用意します。Ansibleを利用する配備には、対応する操作元Pythonも必要です。
SSH接続とホスト鍵を事前に確認し、必要な承認を得て操作します。認証値はこの文書へ記載しません。

下表は操作実装に必要な設定項目です。設定ファイルのキーとして利用できますが、読み込むscriptは対象別に整備します。

| 設定項目 | 内容 | 例 |
|---|---|---|
| ssh_alias | 対象サーバーの許可済みSSHエイリアス | `isucon-target` |
| login_user | SSHログインユーザー | `ubuntu` |
| app_user / app_group | アプリ実行ユーザー・所有グループ | `isucon` / `isucon` |
| webapp | backend言語のソースを含む配置先 | `/home/isucon/webapp` |
| backend_language | 稼働するbackend言語 | `go` |
| backend_dir | webapp内のbackend言語ディレクトリ | `golang`（配置を確認） |
| app_service | アプリのsystemd service | `isu-go`（名前を確認） |
| build_command | 指定SHAから実行ファイルを生成する方法 | 未整備：Goバージョン・ビルド場所を確認して決める |
| backup_root | 配備直前のファイルを保存する場所 | `/home/isucon/deploy-backups` |
| health_url | サーバー内から確認する更新処理のないURL | `http://127.0.0.1/` |
| benchmark_method | benchmarkの開始方法 | 運営Web画面。練習環境にCLIがある場合はSSHエイリアス・引数も記録 |
| benchmark_result | 成否・score・job ID・時刻の確認先 | 未整備：対象問題のマニュアルで確認 |
| results_dir | ローカルの実行結果・ログ保存先 | workspaceの `artifacts/<実行ID>/` |

対象名・初期化方法・DB・ログ配置：未記入。
使用したひな形のcommit SHA・必要なツールのバージョン：未記入。

## 2. 初回benchmark

対象への変更前に実環境のwebappと/etc以下の関連設定を非公開targetへ回収し、秘密情報の除外・復元用metadataを確認してcommit・pushを完了します。DB等の別保全は対象に応じて判断します。初期化・更新を行うbenchmarkも変更に含めます。
保全後、接続先・実行条件・承認を確認し、作業を宣言して計装前の初期状態で早期に実行します。詳細な性能調査や追加計装の完了を待つ必要はありません。
開始手順：未整備。Web画面または対象問題のCLIで実行し、結果の成否・scoreを確認します。CLIでは終了コードも確認します。初期化とDB更新の有無は問題ごとに確認します。
対象・実行時刻・実行条件・成否・score・結果の保存先を記録します。ローカルHEADを配備SHAと見なしてはいけません。

## 3. deploy

実行コマンド：未整備。指定commit SHAを固定し、対象に合うbuild場所と配備方式を確認します。リモートbuildは当日環境の流用が容易で、ローカルbuildは同じ生成物を複数台へ配れる利点があります。既存資産を使い、不要な方式の精密化は後回しにします。
backend言語に必要なビルド・配備ファイル・実行権限を確認します。Goではソースを置き換えるだけで稼働中の実行ファイルが更新されるとは限りません。
復旧元を保存し、アプリを停止して配備・起動・serviceとHTTP応答の確認を行います。依存更新は別途計画します。
認証ファイル・DB・middleware設定はアプリ配備と混ぜません。配備SHA・復旧元ID・結果を記録します。
binaryだけ配備する場合は、実機ソースが旧版のままか、build元commitと実ソースの対応を明記します。ローカルHEAD・実機ソース・稼働binaryを同一視しません。

## 4. rollback

実行コマンド：未整備。配備直前の実ファイルと必要な実行ファイル・権限を復元し、起動とHTTP応答を確認します。
DBや設定変更がある場合、コードだけで復旧できると見なしてはいけません。元の配備SHAが不明なら推測しません。

## 5. 計装後の測定

対象別のコマンド：未整備。初回benchmark後、対象に合うログ形式・slow logなどを一度準備し、調査中は維持する方式を基本にします。必要な復元元を保存し、再起動後は実状態を確認します。

1. 測定前ログを退避・再オープンし、OS指標の採取を開始します。
2. 採取準備完了後、利用者がWeb画面などでbenchmarkを開始します。
3. 結果確定後に採取を終了し、測定ログを回収・解析します。
4. 配備SHA・採取成否と、benchmarkの成否・score・job ID・確認できた時刻を別々に記録します。

採取区間には待機も含みます。受付時刻を負荷開始と見なさず、不明な時刻や配備SHAは推測しません。
測定ごとの設定変更・アプリ再起動を避け、同じ対象で別の測定・変更を重ねません。調査終了時や最終計測前に、対象の条件に従って計装を復元・調整します。
ログ容量を確認し、生ログとSQLの詳細解析はGit外へ保存します。解析のfingerprintも匿名化を保証しません。

MySQLのglobal閾値だけでは既存接続へ反映されない場合があります。アプリ以外のDB利用serviceも確認します。
計装の一時設定は再起動後に戻る場合があります。採取前は現状照合し、不一致を自動修復しません。
counterは開始・終了・PIDを記録して差分を取り、起動後累積・瞬間値・負荷区間の値を混ぜません。

## 6. 改善判断と引き継ぎ

scoreだけでなく、対象SQL/APIの回数・調査行数・平均/p95・エラー・OS負荷を照合します。SQL累計時間は並列実行の合計で、CPU時間とは別です。
正常処理の高速化で副次的な負荷まで増える可能性があります。実測と仮説を分け、score差が小さい場合や新たなエラーがある場合だけ必要な比較を追加します。
問題固有counterの意味はソース・マニュアルで確認します。PASSだけで全APIが成功したとは扱いません。
未検証の別戦略は[タネ箱](STRATEGY-SEEDS.md)、保留時は[再開メモ](RESUME.md)へ記録します。次の実験はレビュー中PRと別branchで進めます。
mainへの統合方法と担当はその練習・チームの合意を記録し、未確定の詳細レビュー体制を必須条件として補完しません。

DB基本操作と対象別の計装scriptは未整備です。
