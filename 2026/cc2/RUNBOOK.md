# CC2 RUNBOOK

状態：チーム確認待ち。

[PLAYBOOK](team/PLAYBOOK.md)の基本原則に沿った共通の操作順序です。Git操作は[Gitワークフロー](team/git-workflow.md)を参照してください。
service名・接続先・配備先・実行コマンドは対象ごとに確認し、非公開の `target/docs/RUNBOOK.md` へ記載します。ここ（`cc2/RUNBOOK.md`）には実環境固有の値や認証情報を置きません。
必要な承認を得てから操作し、LLMの操作には作業場所のAGENTS.mdの承認条件も適用します。

## 1. 開始時の調査

1. 競技・アプリのマニュアルを読み、制約と仕様を確認します。
2. 事前に決めた環境・アプリ・DBの分担に従って調査します。
3. 読み取り調査で、接続先、service、ソース、DB、初期化処理、ログの配置を確認します。
4. 事前に用意した攻略用の非公開リポジトリへ、必要なソース・設定を回収します。認証ファイルや生ログは含めません。
5. 環境情報と操作方法をtargetへ記録し、[開始チェックリスト](checklists/contest-start.md)で確認します。

### 変更前の環境保全

対象インスタンスへ変更を加える前に、実環境の `~/webapp` と `/etc` 以下の関連設定を非公開の `target/` へコピーして退避し、内容を確認してcommit・pushを完了します。回収元・回収時刻・ホストの対応、所有者・権限・symlinkなど復元に必要な情報も記録します。複数台ではホストごとの差分を失わない配置にします。

`/etc` 全体や認証情報を無差別にGitへ入れません。秘密鍵・環境固有の認証値・credentialファイル・生ログを除外し、認証ファイルはパスと非秘密metadataだけを記録します。復旧に必要な秘密情報やDBデータをGitのsnapshotだけで保全できたとは見なしません。必要な別途保全の方法は利用者と確認します。commit・pushにはAGENTS.mdに従う明示的な承認が必要です。

初回benchmarkとの前後関係は対象ごとに決めます。benchmarkがDB・DNS等を初期化・更新する場合も変更として扱い、同一インスタンスでは事前保全を完了します。詳細な性能調査や計装の完了を待つ必要はありません。

本番3台で、保全対象とは別のインスタンスへbenchmarkをかける並行運用は検討案です。DB・DNS・共有ファイルなどの依存を確認し、保全対象へ変更が波及しないことと測定の競合がないことを確認してから採用します。別インスタンスという理由だけで安全とは判断しません。

## 2. 初回benchmark

起動後の動作確認と最初の課題確認を優先し、計装・設定変更は行わず、現行環境で早期に実行します。ログローテートも初回実行の前提にはしません。

1. 対象環境・接続先・実行条件と、前節の変更前保全の完了を確認します。
2. 作業内容を宣言し、他の変更・測定が重ならないことを確認します。
3. 初期状態のままbenchmarkを実行します。
4. 成否・score・実行時刻・実行条件・結果の保存先を記録し、チームへ共有します。

計装後の測定は、初回とは条件を区別して記録します。

## 3. 候補commitのdeploy・測定

1. 候補commitを確定し、対象環境・候補SHA・作業内容を宣言します。
2. 復旧先の既知正常commitと、必要な設定・DBの復旧方法を確認します。
3. 指定SHAの内容を対象へ配備し、必要な起動・再起動と動作確認を行います。
4. ログをローテートし、benchmarkを実行します。
5. 対象環境・配備SHA・変更内容・測定条件・成否・scoreを記録し、結果と必要なログを保全します。
6. 基準と比較してKEEP / REVERTを判断します。KEEPならGitワークフローに沿ってmainへの採用を進め、REVERTなら復旧します。
7. 実行結果と現在の配備状態をチームへ共有します。

deployから結果保全までを一まとまりとして担当し、その間は同じ対象への別の変更・測定を重ねません。
次のログローテートで必要なログを失わないよう、保全を確認してから次へ進みます。

## 4. rollback

1. 対象と復旧内容を宣言します。
2. DB変更がある場合は、コードを戻すだけで復旧できるか確認します。
3. 対象別の復旧手順に従い、既知の正常なコード・設定・必要なDB状態へ戻します。
4. serviceの起動とアプリの動作を確認し、必要に応じてbenchmarkで復旧を確認します。
5. 復旧内容・現在の配備SHA・確認結果をチームへ共有します。

## 5. 最終確認

1. 最終配備する既知正常commitを全員で確認します。
2. 対象へ配備し、サーバー構成・設定・配備内容の整合を確認します。
3. 対象の条件・制約に従って再起動試験を行い、必要なserviceとアプリの動作を確認します。
4. ログローテート・final benchmark・結果保全を行います。
5. [終了前チェックリスト](checklists/final-check.md)を確認し、最終SHAと結果を全員で共有します。
