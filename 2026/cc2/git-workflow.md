# ISUCON Git開発ワークフロー・戦略まとめ

ISUCON（チーム開発）において、コンフリクトを最小限に抑え、デプロイと試行錯誤のスピードを最大化するためのGit運用マニュアルです。

---

## 1. 基本のブランチ設計

ISUCONでは時間ロスの原因となる「共用devブランチ」は作成しません。

*   **`main` ブランチ**
    *   常にベンチマークを実行できる「動くコード」を維持する絶対聖域。
*   **`dev-メンバー名` ブランチ（例: `dev-hidetake` / 固定・計3本）**
    *   **ここを基本の作業場にする。**
    *   タスクごとに新しくブランチを切る時間を削減するため、競技終了までこの固定ブランチを使い回す。
*   **`try-nginx-cache` などの実験ブランチ（アディショナル）**
    *   「大幅なリファクタリング」や「動かなくなるリスクの高い大改造」を行う時だけ、自分の `dev-*` ブランチから一時的に切り出して使い捨てる。

---

## 2. 開発中のルーティン（各自の固定ブランチでの作業）

### 💡 他人の変更を「まめに」手癖で取り込む
自分が作業している間も、他のメンバーが `main` を更新した通知（口頭・Slack等）を聞いたら、**ブランチを切り替えずに**その場で以下を実行する。

```bash
git fetch origin main
git merge origin/main
```
> **効果:** 自分のブランチを常に最新の `main` ベースに保てるため、最終マージ時のコンフリクト確率をほぼゼロにできる。

---

## 3. `main` ブランチへの合流（マージ）戦略

状況（競技の時間帯）に応じて2つのルートを使い分ける。

### 🛡️ 通常時（中盤まで）：安心のPR（プルリクエスト）ルート
1.  自分のブランチをプッシュ:
    ```bash
    git push origin dev-メンバー名
    ```
2.  GitHub上で **main ⬅ dev-メンバー名** のPRを作成。
3.  GitHubが自動で衝突を検知。メンバーに合意を貰い、Web上のボタンでマージ。

### 🏎️ 終盤・緊急時：最速の直接プッシュルート
1.  ローカルの `main` に切り替えて最新状態にする:
    ```bash
    git checkout main
    git pull origin main
    ```
2.  自分の作業ブランチをマージする:
    ```bash
    git merge dev-メンバー名
    ```
3.  GitHubに送信する:
    ```bash
    git push origin main
    ```

---

## ⚡ 4. コンフリクト（衝突）が発生した場合の超速解消法

`git merge` や `git pull` で `CONFLICT` が発生した際
ファイルを開き、エディタ上のボタン（「現在の変更を受け入れる」等）で修正し、以下を実行。
```bash
git add .
git commit -m "Fix conflict"
git push origin main
```

---

## 🔄 5. ベンチマーク実行時のチームの鉄則（先祖返り防止）

1.  ベンチを回したい人が**「今からベンチ回すよ」**と口頭でチームに宣言する。
2.  対象の全サーバー（1〜3号機）で `git pull origin main` を実行し、**全環境を完全に最新状態**にする。
3.  アプリやミドルウェアを再起動する。ログをローテート。
4.  ベンチマークを実行する。
5.  この辺自動化OK。
